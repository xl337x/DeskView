# Code reviews: every finding, the judge's verdict, and why

How these were made: independent critic agents each reviewed one area read-only and reported concrete failure
scenarios; then ONE judge opened the code, verified every claim, and decided what is real and what the correct
fix is. Kept verbatim so a future session knows what was considered, what was done, and what was rejected (and why).
All "fix" items below were implemented (commits 8d13a2d, ca2e576, 283ec9e, 1634f9e, 62c97d1, 321b39e).

## Round 1 - review of the whole app (critics: pictures, input, install)

### Judge: fixes (most important first)

1. **[critical] FFmpeg is looked up next to powershell.exe, so a fresh PC with no ffmpeg on PATH gets no video at all** (`app/Core/Media.cs:21`)

   - Why: I confirmed this. The app is hosted in powershell.exe, so AppDomain.CurrentDomain.BaseDirectory is C:\Windows\System32\WindowsPowerShell\v1.0\. Setup installs the pinned build to %LOCALAPPDATA%\DeskView\ffmpeg (DeskView-Setup.ps1:226). DeskView.ps1 sets DESKVIEW_APPDIR and Program.AppDir reads it, but Tools.Find never uses it. On a PC without ffmpeg on PATH, HasFFmpeg is false and nothing streams, yet setup still prints 'Done'. This machine works only because the winget yt-dlp.FFmpeg build is on PATH (the reports show that ffplay path). Because of that, the pinned, checksum-verified build is never used here either.
   - Fix: Tools.Find: first try Path.Combine(Program.AppDir, "ffmpeg", name + ".exe"), then the current BaseDirectory, then PATH, then WinGet Links. In setup (line 227-228), always prefer and install the pinned build into $ffDir, and use a PATH ffmpeg only as a runtime fallback. Add a test: run DeskView.ps1 -LoadOnly with PATH stripped of ffmpeg and DESKVIEW_APPDIR pointing at a folder holding ffmpeg\ffmpeg.exe, then assert that Tools.Find("ffmpeg") resolves inside it.

2. **[critical] Built-in engine: whenever any picture is live, every server key goes to the laptop, wherever the pointer is** (`app/DeskView-Input.cs:1007`)

   - Why: I confirmed this. In KeyHook, fwd = Forwarding || (RemoteOwned && Connected), and Forwarding = Active && Connected. UpdatePortals (Engine.cs:503) sets Active=true as soon as one player is Live. Smart screens make a picture live automatically when a laptop window touches an extra screen (InputEngine defaults to 'DeskView', so Builtin is true). From then on, typing into a server app on another monitor is swallowed and typed on the laptop. Only the mouse path checks InPicture.
   - Fix: Add 'volatile bool kbdRemote' to DeskViewForwarder, with focus following the click. In MouseHook's Forwarding branch, a forwarded button press inside a picture sets kbdRemote=true, and a press outside every picture rect (which passes locally) sets kbdRemote=false. Reset it to false whenever Active goes false (in the timer's fwd-transition block). In KeyHook use bool fwd = (Forwarding && kbdRemote) || (RemoteOwned && Connected). Keep the hotkey check before it as now. Track keys whose down was forwarded (see the stuck-input fix), so a key-up after kbdRemote flips still goes to the side that got the down. The client 'view' player covers its whole screen and can keep kbdRemote=true while Active.

3. **[critical] A frozen or dead stream is never detected: the report grows ~30 lines/s even with no frames, there is no SRT read timeout and no -autoexit, and ReadInfo rereads the whole growing report 4 times a second** (`app/Core/Media.cs:276`)

   - Why: I confirmed this on this machine. %TEMP%\deskview-ffplay-DISPLAY1.log is 11.7 MB, and its tail is stats lines with fd=14527, vq=0KB unchanged ('6220.48 M-V: -0.016 fd=14527 ...'). So the length check at 277 never sees a stall and the freeze branch at 278 never runs. Without -autoexit and an SRT 'timeout', ffplay never exits on a dead link or when it connects but gets no data (it stays at 'connecting...' forever, and Fails/no-picture/give-back never trigger). Separately, ReadInfo (line 283/301) does ReadToEnd of a file that grows about 7 MB/h, on every 250 ms tick for every player, on the UI thread, even after RemoteRes is known.
   - Fix: (1) Line 226: append "&timeout=4000000" (libsrt read/write timeout in µs) to the caller URL. (2) Line 237: add "-nostats -autoexit " to the ffplay arguments. A stalled or closed stream then ends ffplay with a read error, and the restart path at 247 takes over. (3) Delete the ReportLen/ReportGrew freeze branch (lines 276-282). With -nostats the report stops growing after the header, so leaving it in would kill healthy players every 6 s. (4) Add a start-up watchdog: if (pl.RemoteRes == null && (DateTime.Now - pl.LastStart).TotalSeconds > 12) { pl.Fails++; Kill(pl.P); pl.P = null; if (pl.Host != null) pl.Host.Release(); continue; }. (5) Call ReadInfo only while pl.RemoteRes == null. Once size and rect are parsed, stop reading the file for that run.

4. **[high] When a player dies, freezes or restarts, the forwarder rect, drop zones and portal are not updated, so the visible local desktop stays an input trap** (`app/Core/Media.cs:247`)

   - Why: I confirmed this (two critics reported it). The exit path (247-258), the !Holding kill (272-275) and the freeze kill (278-282) all hide the host and/or null RemoteRes, but none sets changed=true. Engine.Tick (598) therefore never runs UpdatePortals or UpdateDropZones, and the slow tick does not either. forwarder.Active stays true with the old VidL/T/W/H, so clicks and wheel on the now-visible server desktop are swallowed and sent to the laptop. The 1%-opacity drop zone also stays over the area. In classic mode, PortalValue (Engine.cs:453) includes non-live players, and PictureRect returns the whole monitor for them, so a monitor still 'connecting' already hands the cursor over.
   - Fix: In ServicePlayers, capture bool wasLive = pl.Live at the top of each iteration. Move the body into a helper that returns its own 'changed', then do changed |= bodyChanged || (pl.Live != wasLive), so every continue path is covered. In Engine.UpdateDropZones, use p.Live instead of p.RemoteRes != null at lines 528 and 530. In PortalValue (453), use Media.Players.Values.Where(p => p.Live). As a safety net, call UpdatePortals() and UpdateDropZones() in the 2 s slow tick.

5. **[high] Forwarded buttons and keys are left held on the laptop when forwarding stops (Active false, picture dropped, smart screen given back)** (`app/DeskView-Input.cs:742`)

   - Why: I confirmed this. The agent tracks heldButtons and heldKeys but releases them only on disconnect, Leave, or 'X' while edgeIn != null (564). In picture mode, edgeIn is null, so 'X' does nothing. When Active flips false mid-drag, the timer only clears forwardedDown locally. The physical release then goes local, and the laptop keeps its left button or Shift down until the TCP session ends.
   - Fix: Agent Handle(): add case "U": ReleaseAll(); break;. Older agents ignore unknown verbs, so this is safe. Forwarder timer (line 742): when fwd goes true->false and Connected, Enqueue("U") before clearing forwardedDown. Also Enqueue("U") in TakeBack/ComeBack and whenever kbdRemote goes true->false. In MouseHook, check 'if (!down && b >= 0 && forwardedDown[b])' before the Forwarding gate, so a release still reaches the side that got the press.

6. **[high] Built-in engine: only the first live picture accepts input; the other monitors showing laptop screens are dead, and clicks there reach ffplay** (`app/Core/Engine.cs:498`)

   - Why: I confirmed this. UpdatePortals uses Media.Players.Values.FirstOrDefault(p => p.Live), so a single rect and a single 'S n' are set. With smart screens showing laptop screens 2, 3 and 4 on three monitors, only one of them is usable. Clicks on the others pass through to ffplay's adopted SDL window, where a double-click toggles ffplay fullscreen and breaks the picture. On the agent, 'S' is applied only through the client's UI tick (TakeRequestedMonitor), so just re-sending S per move would map moves to the wrong screen for up to 250 ms.
   - Fix: Give the forwarder an immutable array of (Rectangle rect, int screen), swapped atomically as one reference instead of the 4 separate volatiles, and fill it from every Live player. In MouseHook, find the entry under the cursor and send a new verb 'MS <screen> nx ny'. The agent handles MS on its own thread by mapping through Tools.SharedScreens()[screen-1].Bounds, so no UI round trip is needed. Old agents ignore MS, so for them also send 'S n' plus 'M' when the screen changes. Buttons and wheel go to the screen of the last MS. Over any picture rect, swallow local clicks even before the first move, so ffplay never receives them.

7. **[high] 'Start at login' writes 'powershell.exe --tray' to the Run key, which shows an error console at every sign-in and does not control the real startup entry** (`app/Core/TrayApp.cs:101`)

   - Why: I confirmed this. HKCU\...\Run\DeskView on this machine is currently "C:\WINDOWS\System32\WindowsPowerShell\v1.0\powershell.exe" --tray (Application.ExecutablePath is powershell.exe). DeskView really starts from the Startup .lnk that setup creates (Setup:310). Unticking the option leaves the .lnk in place, and uninstall (178) removes the .lnk but never the Run value.
   - Fix: ApplyStartAtLogin should own the same mechanism that setup uses. Create or delete %APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\DeskView.lnk with target powershell.exe and arguments -NoProfile -WindowStyle Hidden -ExecutionPolicy Bypass -File "<Program.AppDir>\DeskView.ps1" -Tray (WScript.Shell through dynamic COM, or IShellLink). Always delete any legacy Run\DeskView value. In the setup uninstall, also run Remove-ItemProperty HKCU:\Software\Microsoft\Windows\CurrentVersion\Run -Name DeskView -ErrorAction SilentlyContinue.

8. **[high] Uninstall leaves the virtual display device, its invisible extra screens and the machine-wide TrustedPublisher certificate** (`app/DeskView-Setup.ps1:131`)

   - Why: I confirmed this. The -RemoveRules elevated part only removes firewall rules. A laptop with 3 extra screens keeps three invisible monitors after uninstall, so windows, dialogs and the pointer can be lost on them. The signer certificate added at line 96 stays trusted for the whole machine, and C:\VirtualDisplayDriver stays as well.
   - Fix: When adding the certificate, write its thumbprint to C:\VirtualDisplayDriver\deskview-cert.txt (or a ProgramData file). In -RemoveRules, find the Root\MttVDD devices with Get-PnpDevice and run 'pnputil /remove-device <InstanceId>' on each. Run 'pnputil /delete-driver <oemNN.inf> /uninstall /force' for the driver whose original name matches MttVDD (from pnputil /enum-drivers). Remove only the recorded thumbprint from LocalMachine\TrustedPublisher. Delete C:\VirtualDisplayDriver. Make the main uninstall call this part whenever the device or folder exists, not only when firewall rules exist, and delete the marker file only after this succeeds.

9. **[medium] The laptop's occupied screens survive a disconnect, so smart-screen monitors are held forever for a computer that is gone** (`app/DeskView-Input.cs:428`)

   - Why: I confirmed this (two critics reported it). Serve's finally clears edgeIn and clipIn but not OccupiedScreens or ScreenCount. ServiceSmartScreens keeps seeing the screens as busy, so the 3 s give-back never runs. The players were EverLive, so the 6-failure give-back is skipped too. The monitors stay on 'connecting...' and ffplay restarts every 2 s indefinitely.
   - Fix: In the wasActive block (line 428), set OccupiedScreens = ""; (not null, because "" means nothing is busy, so autoShown monitors return after the existing 3 s grace). Leave ScreenCount as it is, because the menus still want the last known count. The client re-reports within 5 s of reconnecting (ReportOccupied's 5 s resend), so the screens come back automatically. Optionally, back off player restarts while CurrentPeer() is empty (2, 4, 8 s, up to 15 s).

10. **[medium] Smart screens and the never-live give-back fight each other: the monitor is given back and taken again every ~25 s, with toasts each time** (`app/Core/Engine.cs:595`)

   - Why: I confirmed this. Line 595 removes S.Screens[mon]. On the next tick, ServiceSmartScreens drops the autoShown entry (371), sees n still busy and not in userReleased, and runs ApplyScreen(mon, n) again with a new 'is now on monitor' toast. This happens when the client reports a screen that it cannot stream (no DXGI output, ddagrab failing, port blocked).
   - Fix: Add 'readonly Dictionary<int, DateTime> smartFailed' to Engine. In the give-back loop (591-597), when S.Role == Server and autoShown contains pl.Key, set smartFailed[pl.RemoteN] = DateTime.Now. In ServiceSmartScreens, skip n while smartFailed holds it and less than 5 minutes have passed, and remove the entry when n leaves busy (next to the userReleased.RemoveWhere call). Show the warning toast only once per screen per cooldown.

11. **[medium] A modifier held while crossing the edge (or while focus moves into a picture) stays stuck down on the local machine** (`app/DeskView-Input.cs:1032`)

   - Why: I confirmed this. TryEnter refuses only held mouse buttons. A key whose down passed locally (for example Ctrl or Shift held while flicking to the edge) has its up forwarded and swallowed (return 1). Windows never sees the release, so Ctrl+click and Ctrl+wheel-zoom happen locally after coming back. The keyboard-focus fix above creates the same transition.
   - Fix: In KeyHook, keep a HashSet<int> localDown (only touched on the hook thread). When !fwd and physical: add vk on down and remove it on up. When fwd and physical and !down and localDown.Remove(vk): return CallNextHookEx without forwarding. Do the reverse with a remoteDown set: when !fwd and an up arrives for a vk in remoteDown, forward it (Enqueue K .. 0) and swallow it. That also gives the 'U' fix an exact list of keys.

12. **[medium] Built-in engine: the guide strip's buttons cannot be clicked because the hand-over rect covers the strip** (`app/Core/Engine.cs:500`)

   - Why: I confirmed this. PortalValue cuts StripHeight for classic mode, but the builtin branch copies the full PictureRect into VidL/T/W/H. Presses on 'Give this monitor back' or 'All back' are InPicture, so they are swallowed and sent to the laptop as clicks near the top of its screen.
   - Fix: Add separate hit-test fields to the forwarder (HitT/HitH, or the hit rect inside the per-picture entry in the multi-picture fix). InPicture uses the hit rect, and the normalisation in MouseHook keeps using the full Vid rect, so the mapping stays correct without rescaling. Set the hit top to max(r.Y, Screen.Bounds.Top + MonitorStrip.StripHeight) when S.ShowGuide is on. Use one helper for this and for PortalValue's cut.

13. **[medium] Adopt never checks that the cross-process SetParent worked, so a failure becomes an endless black-monitor and restart loop with no fallback** (`app/DeskView-Portal.cs:420`)

   - Why: I confirmed this. The SetParent return value is ignored, and Show() runs anyway. On the next tick, Holding sees GetParent != Handle, and ServicePlayers kills and restarts the player. RemoteRes is usually parsed, so Fails resets and nothing escalates. SetParent across processes fails on mismatched DPI awareness contexts (the host thread's context can differ from ffplay's PMv2 when the process context was already set by the powershell host) or when the window has already been destroyed.
   - Fix: Make Adopt return bool. After SetParent, if the result is IntPtr.Zero or GetParent(w) != Handle, restore the original style with SetWindowLong(w, GWL_STYLE, style), do not Show(), and return false. In ServicePlayers, on false, increment pl.AdoptFails. After 2 failures, set pl.Passive=true without a host (leave ffplay top-level, call DeskViewPortal.MakePassive on it, and re-assert HWND_TOPMOST in the slow tick), and Log.Write the reason. Create the host with SetThreadDpiAwarenessContext(PerMonitorV2) around its construction (restore afterwards), so it matches SDL_WINDOWS_DPI_AWARENESS=permonitorv2.

14. **[medium] A half-open link (laptop sleeps, Wi-Fi drops) is noticed only by TCP timeouts while all local input is captured** (`app/DeskView-Input.cs:784`)

   - Why: I confirmed this. The reader has ReceiveTimeout=0, and the agent never sends spontaneously. While RemoteOwned, only a blocked write (5 s SendTimeout once the buffer fills) or TCP retransmission expiry ends the session. Meanwhile the pointer is parked and hidden and every key is swallowed. While the writer is blocked, the 4096-item queue's TryAdd silently drops key-up and button-up messages.
   - Fix: Agent: case "P": Send("P"); (it replies '<P'). Forwarder: ping every 1 s while RemoteOwned || Forwarding (5 s otherwise) and record lastHeard in OnAgentMessage for every frame. After the first '<P' has ever been received (so old agents still work), throw IOException('no answer') in the write loop when DateTime.Now - lastHeard > 3 s. The finally block already calls ComeBack. Use a separate unbounded queue for K, B and U messages, so only moves can be dropped.

15. **[medium] Setup: the extra-screens 'asked once' marker is written before anything succeeds, and a ghost or broken device counts as chosen** (`app/DeskView-Setup.ps1:66`)

   - Why: I confirmed this. Ask-ExtraScreens writes the marker before Run-Elevated. If the user declines UAC, winget is missing or the driver is blocked, every later update skips the question. Test-ExtraScreensChosen (59) uses Get-PnpDevice without -PresentOnly or a Status check.
   - Fix: Write the marker only after Run-Elevated succeeds, or immediately when the answer is 0, and store '<count> ok'. In Test-ExtraScreensChosen, return true only if the marker says ok, or if a device from Get-PnpDevice -PresentOnly has Status 'OK'. On failure, print a final yellow 'Extra screens: NOT added (<reason>) - rerun setup' instead of the plain green 'Done'. Skip elevation for an answer of 0 when no device exists.

16. **[medium] Setup stops the running DeskView before the FFmpeg download, so a failed download (or any later throw) leaves the user with no DeskView** (`app/DeskView-Setup.ps1:238`)

   - Why: I confirmed the ordering. Stop-DeskView and the copy run in step 2, before the FFmpeg throw at 238 and the role and code throws at 269 and 297. A failure then exits with DeskView killed and never restarted.
   - Fix: Gather role, code and extra-screens answers first. Download and verify FFmpeg into a staging folder before calling Stop-DeskView. Wrap stop, copy and start in try/finally so DeskView.ps1 is restarted (the old one, or the new one if the copy completed) if anything throws. Also set [Net.WebRequest]::DefaultWebProxy.Credentials = [Net.CredentialCache]::DefaultNetworkCredentials before downloading, and accept -FFmpegZip <path> (still SHA256-checked) for offline installs.

17. **[medium] File transfer reports 'Sent' without any acknowledgement, and dropping a drive root crashes** (`app/DeskView-Input.cs:1222`)

   - Why: I confirmed this. Send returns null right after writing BYE. A receiver failure (disk full, a name collision with a directory, 'more data than announced' from a growing file) just drops the connection, but the user is still told 'Sent'. For p = "D:\\", Path.GetDirectoryName("D:") returns null, so root.Length throws a NullReferenceException (line 1185). Sending until EOF instead of the announced length aborts the whole batch when a file grows.
   - Fix: Receiver: after 'BYE', Send '<DONE n' on the file session stream (write a frame through the same keys). On an exception, try to write '<ERR reason' before closing. Sender: after BYE, read one frame with a 15 s timeout. If it is DONE, report success; if it is ERR, report the reason; if it times out, report 'sent, not confirmed' (older receivers). Send exactly 'len' bytes (stop reading at len; if the file shrank, fail that file clearly). Use root = Path.GetDirectoryName(...) ?? p.TrimEnd('\\') for drive roots.

18. **[medium] The clipboard never syncs while working through a picture; it syncs only on edge crossings** (`app/DeskView-Input.cs:892`)

   - Why: I confirmed this. clipToSend is set only in TryEnter, and the agent sends only in Leave. In the main smart-screens workflow (absolute 'M' input over a picture), copy and paste between the two machines never syncs.
   - Fix: When kbdRemote goes false->true (from the keyboard fix), set clipToSend=true. When it goes true->false, Enqueue("CQ"). The agent handles CQ by calling SendClipboardIfChanged() (old agents ignore it). Longer term, use AddClipboardFormatListener on both sides, push changes debounced by about 300 ms while connected, and keep the existing lastClip echo suppression.

19. **[low] Reinstalling with the other role silently reuses this computer's old pairing code** (`app/DeskView-Setup.ps1:294`)

   - Why: I confirmed this. Get-KnownCode ignores the role. With an explicit -Role that differs from the role stored in app.json, the old code passes the pattern check and the user is never asked for the new server's code.
   - Fix: Always read $knownRole (move that read out of the 'if (-not $Role)' block). Use $known only when $knownRole is $null or equals $Role. Otherwise, set $known = $null and print 'Role changed: the old pairing is replaced.'

20. **[low] A corrupt app.json is silently replaced with defaults, which on a server mints a new pairing code** (`app/Core/AppSettings.cs:162`)

   - Why: I confirmed this. Load swallows every exception and returns new AppSettings(). The wizard then generates a new code and Save overwrites the only copy. Save itself is mostly called inside Tick's try/catch, so the MessageBox flood the critic describes is overstated.
   - Fix: On a deserialize failure, copy app.json to app.json.corrupt-<yyyyMMddHHmmss>, Log.Write it, and try app.json.bak. In Save, pass FilePath + ".bak" as the backup argument of File.Replace, retry up to 3 times with a 100 ms sleep on IOException, and never throw.

21. **[low] Cross-process window calls run synchronously on the UI thread, so a hung ffplay can stall the engine tick that is supposed to kill it** (`app/DeskView-Portal.cs:442`)

   - Why: This is plausible. MoveWindow on another process's child sends a synchronous WM_WINDOWPOSCHANGING to ffplay's thread. Fit runs every tick through Holding, so a hung ffplay (GPU or driver stall) blocks Tick. Host.Close() straight after an asynchronous Kill destroys a parent that still has a foreign child.
   - Fix: In Fit, call SetWindowPos(child, IntPtr.Zero, 0, 0, w, h, SWP_NOZORDER|SWP_NOACTIVATE|SWP_ASYNCWINDOWPOS (0x4000)). In Holding, if IsHungAppWindow(child) is true, return false, so the player is killed and restarted. In StopPlayer, Kill, then p.WaitForExit(500), then Host.Hide(), then Host.Close().

22. **[low] -hwaccel d3d11va never takes effect with this ffplay (Vulkan renderer); decode is silently on the CPU** (`app/Core/Media.cs:228`)

   - Why: I confirmed this in every report: 'Enable vulkan renderer to support hwaccel d3d11va' followed by 'Derive d3d11va from vulkan not supported.' Three 1080p60 pictures decode in software, and the 'Fails < 4 = GPU' escalation is meaningless.
   - Fix: After a player goes live, check its report once. If it contains 'not supported' next to hwaccel, set a session flag (or cache it in settings, as Encoder() does) to try '-hwaccel vulkan' next, and if that also reports unsupported, use no -hwaccel. Make the hw string come from this probed value instead of pl.Fails < 4.

23. **[low] The picture host is never re-raised, so the taskbar or another topmost window covers part of the picture while clicks there still go remote** (`app/Core/Engine.cs:619`)

   - Why: I confirmed this. The strip is re-raised every 2 s and the drop zone on every change, but the host only when it is first shown. Clicking the taskbar puts it above the host.
   - Fix: In the slow tick, before UpdateStrips, call SetWindowPos(host.Handle, HWND_TOPMOST, 0, 0, 0, 0, SWP_NOMOVE|SWP_NOSIZE|SWP_NOACTIVATE) for each pl.Host that is Visible, then re-raise the drop zones, then the strips, so the order is host < zone < strip.

24. **[low] The agent sends a large clipboard before 'L', so the hand-back waits for the clipboard transfer** (`app/DeskView-Input.cs:538`)

   - Why: I confirmed the ordering. Leave reads the clipboard (up to its timeout) and writes up to about 100 x 40 KB frames, and only then sends 'L'. The server stays RemoteOwned (pointer hidden, keys swallowed) for the whole transfer on slow Wi-Fi.
   - Fix: In Leave, send 'L' first: ReleaseAll(); edgeIn = null; Interlocked.Increment(ref Switches); Send("L " + along); and only then SendClipboardIfChanged().

25. **[low] The forwarder reads the clipboard on the low-level hook thread** (`app/DeskView-Input.cs:731`)

   - Why: I confirmed this. The comment says 'never on this input thread', but DvClip.GetText(300) waits up to 300 ms on hookThread, which dispatches the LL hooks. A clipboard owner that renders lazily stalls system input right at the hand-over and risks Windows removing the hook. Hooks are not reinstalled while forwarding.
   - Fix: Make the send asynchronous. Queue a work item to the DvClip STA worker that reads the text, compares it with lastClip under a lock, and Enqueues the CB/CD/CE frames itself. The hook thread only sets the request.

26. **[low] Moving a screen to another monitor tears down and reconnects the stream** (`app/Core/Media.cs:205`)

   - Why: I confirmed this. The key is the monitor, so moving remote screen N to another monitor kills the player. The single-caller listener restarts, and the new caller often waits for its 3 s connect_timeout, which leaves several seconds of black. The critic's claim that this reaches the legacy URL is overstated, because Fails usually reaches only 1.
   - Fix: In SyncPlayers, before stopping players whose key has gone, look for an orphaned Player with the same RemoteN and move it to the new key. Set Screen to the new monitor and Host.Bounds to the new bounds (Fit resizes the child), and keep ffplay running. Restart only in Stretch mode, where -vf scale depends on the monitor size.

### Judge: rejected

- **Design: warm standby players and a 2 s key-frame interval delay a window dragged onto an extra screen** - The GOP is already 30/60 in the uncommitted working tree. Warm players for every candidate screen cost constant bandwidth and decode for a gain of 1-2 s. Revisit only after the timeout and watchdog fixes are in.
- **Duplicate: forwarder.Active and the picture rect stay stale after a player dies (input lens)** - This is the same defect as the pictures-lens finding, merged into the 'Live flip does not update portals' fix.
- **Duplicate: occupied screens survive a disconnect (input lens, low)** - Merged into the OccupiedScreens disconnect fix.
- **ReadInfo whole-file reads and report growth (separate finding)** - This is real, but it is merged into the frozen-picture fix (-nostats, and stop reading once RemoteRes is known).
- **No timeout while connecting (separate finding)** - This is real, but it is merged into the frozen-picture fix (SRT timeout plus a 12 s start-up watchdog).
- **Settings in roaming %APPDATA% are shared through domain roaming** - This is speculative for this deployment, and moving the settings folder adds migration risk. Revisit only if roaming AppData or folder redirection is confirmed on the server.
- **Running setup as SYSTEM (Intune or RMM) installs into the system profile** - Speculative: setup is interactive and per-user by design. A one-line refusal when IsSystem is true is optional hardening, not a fix.
- **Port-only firewall rules are overridden by program Block rules** - Speculative. Deleting Block rules for the generic powershell.exe is too invasive. Revisit only if a connectivity failure is actually observed.
- **Virtual screens depend only on an unpinned winget package** - This is a valid robustness gap, but it needs a mirrored, signed driver release, so it is lower priority than the bugs above. Do it after fixing the marker and uninstall flow.
- **Two UAC prompts, and every start recompiles the app** - A minor UX issue. The in-memory compile is the intended 'no exe to sign' design, and caching a DLL adds AV and signing problems without a concrete failure seen here.

### Raw critic findings (36)

- [critical] Built-in engine sends the server's whole keyboard to the laptop whenever any picture is live, wherever the pointer is (smart screens make this happen on their own) (`app/Core/Engine.cs:503`) - scenario: Server the server with 3 monitors, default InputEngine=DeskView, SmartScreens=true. On the laptop the user drags a window onto extra screen 2. ReportOccupied sends 'O 2', ServiceSmartScreens calls ApplyScreen(monitor1, 2), SyncPlayers runs, then UpdatePortals (builtin branch) sets forwarder.Active=true. From then on KeyHook (DeskView-Input.cs:1007, fwd = Forwarding = Active && Connected) swallows every physical key and sends it to the laptop (line 1032-1036), even while the pointer is on monitors 2 and 3 working on the server's own apps. Typing in a server window lands on the laptop. Only the mouse checks InPicture; the keyboard never does. This keeps going until the laptop window leaves screen 2 or the user presses Ctrl+Alt+0.
- [high] Only the first live picture can be used; the other monitors that show laptop screens are dead, and clicks on them reach ffplay (`app/Core/Engine.cs:498`) - scenario: Smart screens put laptop screens 2, 3 and 4 on server monitors 1, 2 and 3. UpdatePortals (builtin) picks Media.Players.Values.FirstOrDefault(Live), sets VidL/T/W/H to that one rect and 'S n' to that screen. Moving over monitors 2 and 3 sends nothing (InPicture is false), and clicks there go locally into ffplay's adopted SDL child window. ## Round 2 - review of the round-1 fixes (critics: media, input, setup)

### Judge: fixes (most important first)

1. **[high] Liveness check falsely drops the link right after forwarding starts (idle 5 s pings vs 4 s timeout) and after a long clipboard write** (`app/DeskView-Input.cs:890`)

   - Why: Verified. lastHeard is only refreshed by agent messages (line 1087). While the link is idle, pings go out every 5 s, so lastHeard can be up to about 5.1 s old. As soon as Forwarding or RemoteOwned turns true, every becomes 1. In that same loop pass a P is written and (now - lastHeard) > every+3 = 4 is tested, which throws 'stopped answering'. The finally block then calls ComeBack, so the pointer snaps back. That hits roughly 1 crossing or picture click in 5. The same false drop happens when the drain loop takes more than 4 s to write a big clipboard, because no ping goes out during the write.
   - Fix: Time the timeout from the oldest unanswered ping. (1) Replace the field 'DateTime lastHeard = DateTime.Now;' with 'long lastHeardTicks = DateTime.Now.Ticks;' and in OnAgentMessage replace 'lastHeard = DateTime.Now;' with 'Interlocked.Exchange(ref lastHeardTicks, DateTime.Now.Ticks);'. At connect (line 867) set 'Interlocked.Exchange(ref lastHeardTicks, DateTime.Now.Ticks);'. (2) In NetLoop, next to 'DateTime lastPing = DateTime.Now;', add 'DateTime pingSentAt = DateTime.MaxValue;'. (3) Replace the two lines at 889-890 with: 'var heard = new DateTime(Interlocked.Read(ref lastHeardTicks)); if (pingSentAt != DateTime.MaxValue && heard >= pingSentAt) pingSentAt = DateTime.MaxValue; if ((DateTime.Now - lastPing).TotalSeconds > every) { DvProto.WriteFrame(s, keys, ++seq, "P"); lastPing = DateTime.Now; if (pingSentAt == DateTime.MaxValue) pingSentAt = lastPing; } if (agentVersion >= 2 && pingSentAt != DateTime.MaxValue && (DateTime.Now - pingSentAt).TotalSeconds > 4) throw new IOException("the other machine stopped answering");'. pingSentAt is taken after WriteFrame returns, so a long drain burst no longer counts against the agent.

2. **[high] Without -fflags nobuffer, the big-probe path keeps a lasting 0.8-3 s lag** (`app/Core/Media.cs:287`)

   - Why: Verified. mpegts is AVFMTCTX_NOHEADER, so avformat_find_stream_info reads until probesize or analyzeduration runs out: 2 MB, about 0.8 s at 20 Mbit/s and more at 10 Mbit/s. ### Judge: rejected

- **Key frame every 0.5 s gives no benefit and costs picture quality** - The join-time claim is right (each viewer gets a fresh listener that starts on an IDR). But the accepted nobuffer fix for the big-probe path depends on frequent IDRs to start quickly, and the GOP also speeds recovery after loss and discardcorrupt. Keep -g 30/60. Any quality cost is a tuning question, not a regression.
- **ServedViewer resets Fails so a GPU path that fails mid-stream never falls back to CPU** - Speculative. hwmap/encoder failures happen at filter or encoder init, before 'Output #0' is written. The proposed ExitCode==0 test would also count the normal 'viewer left' exit (a write error, nonzero exit) as a failure, which brings back the back-off the commit removed.
- **Clipboard read on the thread pool lets Ctrl+V overtake the clipboard** - The added window is a few ms (DvClip already runs on its own STA thread). The 50 ms tick window already existed before. Moving the read off the LL-hook thread is the correct fix, and holding keys back would add key latency and complexity for a rare case.
- **ApplyStartAtLogin rewrites the Startup .lnk on every launch** - Harmless and idempotent (setup writes the identical shortcut). The EDR concern is speculative. Not a regression of this diff's claims.
- **robocopy /MOVE fallback only checks ffmpeg.exe** - Real, but it is merged into the rename-based FFmpeg swap fix, which drops this fallback and checks Test-FFmpeg plus the stamp file.
- **After restoring from .bak the corrupt app.json stays and the next Save overwrites the good backup** - Merged into the AppSettings.Load fix (copy .bak back over app.json after a real restore).

Without nobuffer, all of those packets are queued and played. With -sync ext, the external clock locks to the first frame's pts, and ffplay only speeds up the clock for realtime inputs (is_realtime() is false for srt://), so the backlog is never caught up. Common case: the server's DeskView starts before the laptop is up, two connects fail (Fails=2), and when the laptop arrives every picture stays 0.8-2 s behind for the whole session, which makes the pointer feel broken. Before this commit nobuffer threw that backlog away. The fast path (32 KB probe, stream starts on an IDR) is fine. ca2e576 narrowed the big probe to !EverLive but the problem remains.
- [medium] ServicePlayers misses the change when a player exits on its own (the new -autoexit / SRT timeout path) (`app/Core/Media.cs:301`) - scenario: Live is RemoteRes.HasValue && P != null && !P.HasExited. If ffplay exits between ticks (a stalled stream with -autoexit, a timeout, a crash), Live is already false when 'bool wasLive = pl.Live' runs. ServicePlayer then takes the exit branch and returns false, so changed stays false. UpdateDropZones, UpdatePortals (forwarder.Pictures and the classic portal), UpdateStrips and OnChanged wait for the 2 s slow tick. In the built-in engine, for up to 2 s the dead picture's area (the host is hidden, so the user sees their own desktop) still swallows clicks and sends them to the other computer (MouseHook returns 1 for a press inside the picture). The near-transparent drop zone also keeps catching clicks there. The classic portal keeps handing the pointer over a monitor that shows the local desktop. The commit claims 'Hand-over areas and drop zones follow pictures appearing/disappearing', but they do not do so promptly.
- [medium] A picture moved to another monitor keeps its old key's report file, so two players share one FFREPORT (`app/Core/Media.cs:247`) - scenario: Example: DISPLAY2 shows screen 2, the user puts screen 2 on DISPLAY3 (ApplyScreen removes DISPLAY2, SyncPlayers moves player A), then puts screen 3 on DISPLAY2. A still writes deskview-ffplay-DISPLAY2.log, and the new player B for DISPLAY2 gets the same path (line 256). StartPlayer's File.Delete fails (A's ffplay holds it open without FILE_SHARE_DELETE), so the next tick's ReadInfo for B can read A's header: screen 2's size and its 'DeskView|2|x,y,w,h' rect. B goes Live at once with the wrong RemoteRes/RemoteRect, so the portal and the letterbox mapping use the wrong screen. Both processes also write into the same file at different offsets. When A later restarts it can likewise read B's header, or find no readable header and get killed by the 12 s watchdog over and over.

- [low] Raising picture hosts every 2 s hides DeskView's own toast on picture monitors (`app/Core/Engine.cs:641`) - scenario: Host.Raise() puts every picture host at the top of the topmost band every 2 s. - [low] Key frame every 0.5 s does not do what the commit message says (no viewer ever joins mid-stream) and costs picture quality (`app/Core/Media.cs:140`) - scenario: Each sender is a fresh ffmpeg listener per viewer. ffmpeg opens the SRT output (avio_open2 in of_open) before transcoding starts, and that call blocks until the caller connects, so the first packet every viewer gets is already an IDR with SPS/PPS. Going from -g 120 to -g 30 at 60 fps (CBR 20M, bufsize 0.5 s) therefore gains nothing at join time. It does pay 4x more I-frames, which shows up as quality pulsing or blur on text every 0.5 s under CBR. It helps only recovery after packet loss, which the commit does not claim.
